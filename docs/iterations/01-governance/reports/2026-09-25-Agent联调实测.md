## 4. 模型取证、失败与修正

| 验证 | 实际情况 |
| --- | --- |
| 主服务故障 | 502 被明确记录；备用实际返回原生 tool_calls，服务切换不重新执行已受理任务 |
| 初始 2048 token 解释 | 已读取真实任务及质量，但回答被截断，返回 MODEL_TRUNCATED，没有把不完整结果标成成功 |
| 早期重复查询 | 一次重试耗尽 6 轮，返回 MODEL_ROUND_LIMIT；随后为最终回答保留一轮，并补全参数说明 |
| 全量自动解释 | tasks.get / artifacts.list / artifacts.get 读取本任务精确质量版本，回复完成；人工复核发现原因合计和分区描述错误 |
| 原始追问 | 再次读取本任务 tasks.get / artifacts.get，无新增治理任务；说明代理分数不证明真实性 |
| 解释修正 | summary 加入 interpretation_facts，由代码计算 R12 总命中数、明确评分去重和分区说明；新回答纠正为 89,939、0、尚未物化 |
| 受理回复改进 | 原全量发起阶段有 6 轮模型调用，其中 4 次重复查询状态；应用现直接根据 accepted 的真实引用生成回执，不再让模型轮询 |
| 首次启动与可选备用 | 空 catalog 可返回无登记数据的正常状态；未配置备用时保留主服务的真实错误，不用“未配置”掩盖 502 |

原始错误回答和更正都保留在 SQLite 会话中。模型的自由文字仍存在公式单位省略等表述问题；不会把历史回答改写成“从未出错”。页面指标、分母、处置量和下载直接读取产物；汇报须采用本报告或质量 JSON 的公式与计数，并审校模型文字。

受理改进另以真实模型验证：1 轮模型调用，约 77.013 秒，返回 application_receipt，任务状态 queued。此检查使用独立的 `var/verification/2026-09-25/receipt.sqlite3`，未启动其 worker，只验证受理语义，不能当成第二次全量运行或稳定延迟基准。
