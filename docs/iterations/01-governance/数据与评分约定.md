# 迭代一：数据与评分约定

**状态：供实现的数据协议与评价方法草案。** 已取得 [首次只读核查结果](reports/2026-09-24-原始数据核查.md)，清洗规则和正式评分尚待验证。字段语义依据课程文档与本地 `ml-1m/README`；规则、评分配置和时间参数在只读核查后登记版本。公共产物引用遵循 [技术方案与接口约定](技术方案与接口约定.md)。

## 1. 输入与来源定位

原始数据按字节保留，只读核查时记录文件名、字节数、内容 SHA-256、物理记录数和来源说明。登记原始数据版本后，运行前核对内容校验值；文件发生变化须登记新版本。

解析采用 ISO-8859-1、无表头、`::` 分隔。物理记录定义为按换行分开的记录，文件末行没有换行仍计一条；空白行单独计数并保留来源。输入总数、可解析记录数和有效记录数分别展示。

来源引用建议采用 `input_version + file_name + byte_offset`，可同时保留行号用于人工查看。Hadoop Streaming 适配器应确保来源信息能跨分片传递；若使用预处理为记录附加来源，其职责限于格式封装，全部业务检查、清洗和正式评分仍由 Hadoop 执行。 建议将每条原始记录及其来源封装为 UTF-8 JSONL，原始字节使用 Base64 保存；Hadoop mapper 再解码并按原编码解析字段。封装阶段不删除、修复或过滤任何记录，核对封装前后记录数，避免输入接口默认 UTF-8 造成静默损坏。

每条记录保留原内容与检查结果。ISO-8859-1 可以解码任意字节，因此“解码成功”不证明文本语义正确；疑似混合编码、乱码或异常标题应记录依据，不能猜测修复。

## 2. 清洗后三表协议

首版建议输出 UTF-8 JSONL，每行一个对象，标识符与时间戳为整数，人口属性编码保留其原始类别语义，邮编为字符串。源数据解析约定和清洗输出编码分别写入清单。

| 表 | 输出业务字段 | 约束 |
| --- | --- | --- |
| `ratings` | `user_id: int`、`movie_id: int`、`rating: int`、`timestamp: int` | 评分 1–5，时间戳单位为秒；关联到发布版本中的用户和电影 |
| `users` | `user_id: int`、`gender: str`、`age_code: int`、`occupation_code: int`、`zip_code: str` | 性别按源数据编码；年龄代码为 1/18/25/35/45/50/56，职业代码 0–20；不把年龄代码解释为实际年龄 |
| `movies` | `movie_id: int`、`title: str`、`genres: list[str]` | 类型从源说明的 18 类中核对；保留完整标题，不强制提取或补写年份 |

每条保留记录附带 `source_ref`；若业务清洗去重后保留代表记录，其他来源及修复历史在处置产物中关联。源说明中的最大标识符或官方记录数用于核查线索，不能直接替代当前课程副本的关联和有效性检查。

数据集清单最少记录三表的文件清单、模式版本、编码、行数、校验值、生成任务、输入版本、规则/评分配置版本和时间边界引用。字段名或编码变化需更新模式版本，并通知后续工具读取方。

## 3. 规则与处置

以下为保守的首版候选规则；核查后按事实确定是否启用、适用字段和具体匹配方法，不能假定原始数据必然具有表中的问题。

| 情况 | 候选行为 | 应保留的依据 |
| --- | --- | --- |
| 可确定的字段首尾空白、类型列表重复项 | 规则显式允许时规范化 | 原值、新值、规则编号，证明不会改变业务含义 |
| 空行、字段数异常、必需字段缺失、不可解析数值 | 隔离，保留原记录 | 文件位置、期望字段数、错误类别 |
| 非法评分或类别编码 | 隔离，或在有确定映射证据时修复 | 值域来源或映射表版本；不猜测用户真实属性 |
| 完全相同的实体或评分事件 | 去重，按稳定来源顺序保留一条 | 保留记录与移除记录的来源关联 |
| 同一用户/电影标识对应冲突属性 | 首版优先隔离冲突组，核查有无可靠消解依据 | 同键记录组、冲突字段、采用规则 |
| 同一用户、电影、时间的评分相互冲突 | 隔离冲突组 | 评分事件键及各个评分值 |
| 同一用户对同一电影在不同时间评分 | 保留为不同事件 | 不仅按用户—电影二元组去重 |
| 评分引用缺失或无法消解的用户/电影 | 隔离，注明原始缺失或主表处置的连带影响 | 关联检查阶段、所引用主表版本、原因 |
| 数据年代较早、评分数量多、标题同名 | 记录统计或疑点，结合场景解释 | 不直接据此删除；先判断是否属于业务上合法的现象 |

建议阶段顺序为：原始核查与评分 → 字段规范化 → 用户/电影重复及冲突处理 → 评分事件处理及重新关联 → 输出核对 → 清洗后评分。阶段可以由多个 Hadoop 作业实现。

处置记录至少包含 `source_ref`、问题标签、最终处置、原因、规则编号、保留记录引用以及适用时的修改前后值。最终处置采用互斥的 `kept/repaired/deduplicated/quarantined`；一个记录可以有多个问题标签和多次变换，但最终只计一次去向。

对于不拆分、不合并、不新增记录的首版规则：

```text
input_rows = output_rows + deduplicated_rows + quarantined_rows
output_rows = kept_rows + repaired_rows
```

被修复后最终隔离的记录按 `quarantined` 计最终去向，变换历史另保留。不能把问题标签计数之和当作移除数量；若后续加入记录拆分或合并，应扩展守恒关系和来源映射。

## 4. 五维评分建议

课程没有指定具体公式。本节给出可实现、可解释的候选口径；正式运行前把检查项、公式、聚合方式、时间参数与例外处理写入版本化配置。Hadoop 计算基础统计及最终分数，应用层负责读取与展示。

单项检查先保存 `population`（检查总量）与 `passed`（符合条件数量），比例分为 `100 × passed / population`。除唯一性外，下面的检查均可按这一形式表达。分母为零时分数为 `null`，并提供状态与原因，不回填 0 或 100。

| 维度 | 候选指标与分母 | 解释边界 |
| --- | --- | --- |
| Accurate | 可核验值约束符合率：评分整数值域、用户性别/年龄段/职业编码、电影类型集合；每条记录按该表固定检查项计入分母，解析或必需值缺失使对应检查不通过 | 页面注明“可验证约束代理”；用户属性真实性、电影事实准确性等未获外部证据的部分另列未验证，不能把代理满分称为真实准确率 |
| Complete | 必需字段完整率：完整字段槽位 / 期望字段槽位；ratings/users/movies 每行分别期待 4/5/3 个字段，不能可靠解析的行按缺失槽位计入 | 原始空白行仍产生该表应有槽位；字段值非法但非空与缺失分开记录；未发生的用户—电影评分不作为缺失项 |
| Unique | 业务键唯一率：`100 × distinct_valid_keys / input_rows`；用户键为 UserID、电影键为 MovieID、评分事件键为 UserID/MovieID/Timestamp；无法构造合法键的记录留在分母 | 同键同值与同键冲突分别报告，不能都按“重复副本已修复”解释；对无有效键造成的下降单独说明 |
| Up-to-date | 固定时间参照下的新鲜记录比例：满足 `reference_time - window_seconds <= timestamp <= reference_time` 的评分行 / 评分总行数；非法或缺失时间不能进入分子 | 只评价有事件时间的 ratings，users/movies 标为不适用；历史场景的参照和窗口需有依据，未来时间不算新鲜，时效性低不自动触发删除 |
| Consistent | 记录约束通过率：各表通过适用的一致性检查的行数 / 该表输入行数；检查结构/类型/单位、同键冲突，评分另检查跨表引用 | 原始检查使用原始主表，清洗后检查使用发布候选主表，逻辑口径一致；解析失败或冲突组中的记录不算通过 |

类型枚举应从数据集说明登记。候选 Accurate 检查中，评分表每行 1 项、用户表每行 3 项、电影表每行 1 项（非空且全部类型合法）；检查项增减时必须升级配置版本。多个维度可能反映同一异常，首版分别展示五维分数，不把它们相加解释为独立错误数量。

建议先报告每表的指标，再对 Accurate、Complete、Unique、Consistent 按三表等权汇总，避免百万行评分表完全掩盖用户和电影问题；权重作为配置持久化。Up-to-date 单独报告评分表结果。某个必需表无法评价时，不静默丢掉该表重分配权重，汇总分标为不可评价并说明原因。

前后评价固定检查项、权重、公式、时间参照、缺失与不可解析记录处理方式。实际分母会随清洗变化，需同时展示分子、分母、保留率及隔离数量。分数改善不能单独证明信息更完整或真实，全部删除数据不能被评为满分。

`reference_time` 与 `window_seconds` 目前未确定，应结合数据来源、合理事件范围和历史分析用途登记；不得把未经检查的最大时间戳直接当作参照，也不在前后两次计算中分别取当前系统时间。

## 5. 质量结果与报告协议

每个维度结果包含：维度名、评价范围、状态、分值、基础统计、指标公式/配置引用、分表明细和局限。维度状态为 `computed/not_evaluable/not_applicable`。`not_applicable` 仅用于该表没有相应业务含义的情况，例如无事件时间的用户属性表；不能用于掩盖缺少计算实现。

只有前后两个分值都存在且口径一致，才计算和展示变化量；其他情况展示原因。程序出错是任务或阶段失败，不伪装成指标“不适用”。空数据可以有真实的诊断报告，但不是完整的正常数据验收结果，后续训练工具应拒绝使用不可用的数据版本。

报告至少包含：

1. 任务与版本：输入/输出、规则、评分配置、代码与 Hadoop 作业引用。
2. 方法：五维公式、权重、分母、参照时间、时间边界、无法核验的事实。
3. 结果：前后指标及其原始统计、各表数量、保留率和处置守恒核对。
4. 依据：有来源的代表性记录、修复/去重/隔离原因、仍未解决的问题。
5. 获取方式：清洗数据及样例、指标、处置记录与报告的产物引用。

大规模处置明细单独存储，前端分页查看。报告内只取有代表性的有界样例，并注明样例不是全部异常数量。

## 6. 时间边界与后续使用

清洗数据保留全部符合规则的历史评分事件，交付清晰的时间划分信息。若首版尚未物化三个分区，数据清单应注明“按时间条件读取”，后续工具不得把全量清洗表当作训练输入。

统一采用 UTC，字段可用 Unix 秒表达：

```text
train:      timestamp <= train_end
validation: train_end < timestamp <= validation_end
test:       timestamp > validation_end
```

要求 `train_end < validation_end`，它们对应课程的 `T1/T2`。具体数值和选择方法待有效时间分布核查后确定，并记录三个区间的实际数量、边界相等时的归属及生成任务。评分的时效参照与训练/验证边界是不同配置项，不能因名称类似而复用。

首版优先使用固定业务规则和确定性修复。若引入由数据学习的填补值、阈值或冲突消解策略，须记录拟合范围且只用训练期证据拟合，再应用到后续期间；不得利用验证/测试评分构造训练特征。任务成功、质量高分和满足训练前置条件分别校验。

## 7. 冻结方案前的证据

| 待确认 | 核查输出 | 对方案的影响 |
| --- | --- | --- |
| 当前数据来源与副本 | SHA-256、文件规模、来源说明 | 固定输入版本；不以官方总数强行修正本地数据 |
| 字段与异常类型 | 解析、缺失、值域、重复、冲突、关联统计及样例 | 确定规则启用项和冲突处置方法 |
| 时间分布与可解释范围 | 有效时间分布、异常时间样例、来源所支持的历史范围 | 确定合理性检查、时效参照和 `T1/T2` |
| 质量评分可解释性 | 对小型已知样例手算与 Hadoop 输出核对 | 确认公式、分母、权重及零分母行为 |

当前核查已确认字段数、值域、同键冲突和未来时间等实际问题。候选规则中的冲突组隔离可能显著影响评分记录数量，需要据核查报告中的关联计数评估处置顺序与损失。

这些候选规则与公式尚未登记为可执行默认配置。应用实现后，只有通过配置校验并登记精确版本的方案才可作为 `governance.run` 的缺省方案。
