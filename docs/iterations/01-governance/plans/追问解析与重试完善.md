# 迭代一：追问解析与重试完善计划

状态：实施中。负责人：duscwalk。日期：2026-09-25。基线：`b4d662e`。

本轮完成当前应用可由开发者自行实现和验证的工作。目标是修正需求解析、消除提示冲突、处理连续样例追问，并让失败后的重新解释有明确入口与审计。成员复现不作为本轮依赖或验收条件。

## 1. 已确认的问题

- “十一条”被解析成一条，“第十一条”落在第一条；复合问题中“两个评分样例和一个用户样例”被统一成各两条。
- “真实样例”会额外触发真实性限制主题；“再给一个”没有使用已展示样例的位置，可能重复第一条或丢失规则。
- 解释 JSON 示例固定 `unsupported=false`，与当前问题可能要求的 `true` 冲突。上一轮简短题仍需一次修正。
- 页面失败后依赖重新手工输入问题；稳定的自动解释请求 ID 会返回原失败，切换任务后手动重发还可能改变目标。
- 原回归主要重复七类固定措辞，对变体、局部数量、指代和重试的覆盖不足。

## 2. 实现约定

### 数量、范围与连续追问

完整识别数词，按每个明确样例目标绑定数量和序号；数字范围、无法确定的数量分配等歧义不默认为一条。继续遵守每次查询 1—20 条、起始偏移不超过 10000 的工具限制。支持明确中文数词、阿拉伯数字及已有英文表达，清洗文件和异常规则分别处理。区分“真实样例”与“能否证明事实真实”。

连续追问仅使用当前会话中最近成功答复的结构化样例要求、实际返回数量、报告引用和消息 ID。必须属于同一任务和精确报告；“再给一个”从已展示范围之后读取，明确的新目标按新范围读取。多种来源未指定其一、缺少前序样例或跨任务指代时，返回澄清提示，不偷偷选择默认来源。需求解析结果及继承依据进入 validation，历史记录不改写。

### 一致的提示与证据处理

JSON 示例根据当前允许要点和无法确认要求生成，空样例也与实际证据保持一致。保留一次修正预算及事实渲染。绑定已完成报告的解释及其重试只允许查询工具，模型不能在这个路径受理新治理任务；明确的新清洗指令继续走原受理流程。

### 失败后的重新解释

增加按失败回答 ID 重新解释的 API 和页面按钮，由服务端取回原问题、原任务及必要的已解析上下文。每次用户主动重试使用新请求 ID；重复发送同一个重试 ID 返回缓存，原失败不覆盖。新的失败继续明确展示，不自动连续重试。

仅允许失败的报告解释进入此入口，不将任务受理或不确定执行状态当作重新提交许可。重试绑定原任务，重新校验当前产物；连续追问重试保留原游标，后续消息不能改变它。页面提供直接查看该任务已发布结果/报告的入口，模型故障期间仍可读取事实。

## 4. 验证矩阵

- 普通测试：完整数词与超限、序号与分页、两个规则/文件的不同数量、“各”与总量歧义、分句否定、真实样例、提示一致性。
- 会话测试：单一来源下一条/再两条、多个来源明确指定与澄清、空分页、跨任务/报告边界、失败后游标保持、原记录与请求缓存不变。
- 重试测试：模型失败后恢复、重复重试 ID、跨会话访问、非解释失败被拒绝、恶意/误选 job 工具被拦截；前端切换任务后仍重试原任务。
- 真实模型：固定备用服务和任务 `064523f8a8bf41a38f7c2193caf59930`，先跑七类原题一次，再跑数量/否定/真实样例/多轮变体；简短题至少三个新请求，记录首次修正率。所有服务错误与内容错误分开统计；每种受影响场景最多另做一次补测。
- 页面：真实新追问及真实已保存失败的重试；可控故障用独立测试 catalog 与模型替身验证交互，明确标记为替身，不计入服务可用性。检查报告入口、刷新、手机宽度及任务数不增加。
