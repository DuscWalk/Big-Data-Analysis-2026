# 作业三：大数据存储和处理的技术选型路线图

本作业以小组为单位完成，每组提交一份。

## 1. 作业定位与边界

本周课程从 Google 三驾马车的设计思想延伸至 Hadoop 生态的具体实现，讨论关系数据库、NoSQL 和全文检索的访问模式差异，行存、列存与倒排索引，HDFS 的节点角色和文件读写流程，MapReduce 处理链路，HBase 的数据模型与 Region，以及 Hive 的数据仓库抽象。

本学期第一次实验要求构建 MovieLens 数据治理 Agent。用户通过前端提交自然语言请求后，Agent 调用 Hadoop 完成数据质量检查、数据清洗和清洗前后的五维质量评分，并返回真实结果及相应解释。

作业一已完成 **问题发现与设计决策**，并输出问题编号 P1、P2 等和设计决策编号 D1、D2 等。本作业以这些内容为输入，聚焦 **具体技术选型**：比较候选技术，并将设计决策落实为系统、组件、数据格式、表结构和部署方式。

| 作业一已经负责 | 本作业负责 |
| --- | --- |
| 给出问题、证据、触发条件、影响和优先级 | 接受问题结论，并比较能够处理相关问题的技术 |
| 给出设计决策、所需能力、约束和验收条件 | 为设计决策选择具体技术 |
| 确定系统所需的存储、计算、查询和恢复能力 | 选择 HDFS、对象存储、MapReduce、HBase、Hive 等技术 |
| 绘制技术中立的逻辑架构 | 绘制组件架构和部署拓扑 |
| 说明哪些问题现在处理、以后处理或暂不处理 | 说明技术的引入、替换、迁移或下线时机 |
| 保留风险和触发重评条件 | 说明技术限制、运维成本和回退方法 |

本作业不再发现或论证作业一已经分析的问题，也不重新作出原则性设计决策。

本作业不要求实现全部入选技术。实验仍以实验文档规定的基础功能为准，完成基础功能即可获得实验部分的满分。架构中的集群、高可用、HBase、Hive、Elasticsearch、对象存储或湖仓能力不会自动成为实验的额外实现要求。

## 2. 总体要求

围绕以下问题完成一份架构设计文档：

> 针对作业一中的问题 P1、P2 等和设计决策 D1、D2 等，哪些具体技术能够满足所需能力与约束？为何从 HDFS、HBase、Hive、MySQL、Elasticsearch、对象存储或其他候选方案中作出相应选择？所选技术应如何组合、配置、部署和迭代？

文档应形成清晰的推理链：

> 问题 P 与设计决策 D → 所需能力与约束 → 候选技术比较 → 技术选型 T → 落地架构 → 分阶段演进

技术选择必须以需求和访问模式为依据，不得先选择产品再寻找用途，也不得通过堆叠组件体现方案的先进性。

## 3. 详细要求

### 3.1 输入与追踪关系

首先整理作业一中的问题和设计决策，形成技术选型追踪矩阵。

| 来源 | 所需能力与约束 | 候选技术 | 比较维度 | 最终选择 | 选择理由 | 未满足项与补救措施 |
| --- | --- | --- | --- | --- | --- | --- |
| P1、D1 | 引用作业一 | 至少两个具体候选方案 | 与来源问题相关的指标 | 明确到具体技术或方案 | 结合证据说明 | 说明限制，不得声称完美解决 |

至少完成 4 项具体技术选型。每项选型必须满足以下要求：

- 至少引用一个 P 编号和一个 D 编号。
- 说明作业一提出的能力与约束。
- 比较至少两个具体候选技术。
- 使用与来源问题相关的维度进行比较，不得只比较知名度。
- 明确最终选择，并说明未满足项和补救措施。

如确有新增需求，应先补充相应问题，再决定是否将其纳入选型。

### 3.2 数据对象与访问需求

至少分析以下数据对象，并分别确定其主存储、处理方式和访问技术：

- MovieLens 原始文件。
- 解析失败或需要隔离的异常记录。
- 清洗后的 ratings、movies 和 users 数据。
- 五维质量指标、规则版本和数据版本。
- Hadoop 任务状态、日志和失败信息。
- 面向用户展示的报告、样例和查询结果。

每个数据对象至少应说明：

| 项目 | 要求 |
| --- | --- |
| 数据角色 | 说明属于权威数据、派生结果、索引、缓存还是临时数据 |
| 写入模式 | 说明采用批量写入、追加、覆盖、随机更新还是流式写入 |
| 读取模式 | 说明采用全量扫描、范围查询、点查、聚合还是全文搜索 |
| 一致性要求 | 说明数据何时必须可见，以及是否允许延迟或重复 |
| 生命周期 | 说明保留时间、版本数量和删除方式 |
| 对应来源 | 关联相应的 P、D 和 T 编号 |

### 3.3 课堂技术与候选方案

以下四部分均须涉及。分析重点是各项技术适合哪些访问需求，以及是否应纳入本系统。

| 课堂主题 | 必须分析的内容 | 需要完成的选型 |
| --- | --- | --- |
| 存储与访问模式 | 行存、列存、倒排索引，块、文件与对象存储，事务与分析工作负载的差异 | 为不同数据对象选择主存储和访问方式 |
| HDFS 与 MapReduce | NameNode、Secondary NameNode、DataNode、Block、副本、读写流程，Map、Sort、Combine、Partition、Reduce | 设计数据目录、作业输入输出、Shuffle 边界和结果发布方式 |
| HBase | HMaster、RegionServer、Region、HStore、MemStore、HFile、WAL、RowKey、Column Family、Timestamp | 判断是否需要在线宽列存储，并设计键、列族、版本和热点处理方式 |
| Hive 与其他访问层 | 表与外部表、元数据、分区、分桶、压缩，关系查询与全文检索 | 确定 SQL 分析、事务查询和全文搜索分别由哪个组件承担 |

某项技术若不适合当前系统，可以不选择，但必须说明依据。课程涉及的技术不必全部纳入架构。

### 3.4 工业界演进调研

除课堂内容外，选择一条相关的工业界前沿技术路线进行调研。建议方向如下：

- HDFS 的高可用、Federation、机架感知、纠删码或 S3A。
- HBase 的 RowKey 热点治理、Region 管理、复制或托管宽列服务。
- Hive 与现代 SQL 引擎、列式文件格式、Metastore 或 Catalog 的协作。
- Parquet、ORC 与行式文本在扫描、压缩、模式和更新方面的差异。
- 对象存储与存算分离对数据本地性、提交协议和成本的影响。
- Iceberg、Delta Lake 或 Hudi 的快照、模式演进、分区演进和事务能力。
- Elasticsearch 等全文检索系统与数据库、数据仓库的职责边界。
- Hadoop/YARN 与容器化、托管服务或弹性集群在部署方面的差异。

所选方向至少应说明：

- 它对应作业一中的哪些 P 和 D。
- 它处理哪类数据，服务哪种读写路径。
- 它如何与现有组件交换数据。
- 哪个组件保存权威数据，哪些组件只保存派生副本。
- 在何种规模、延迟或可用性要求下值得引入。
- 与至少一个候选方案相比，选择或不选择它的理由。
- 它会增加哪些运维、成本、一致性或迁移风险。

### 3.5 技术选型记录

至少写出 4 项具体的技术选型记录。

~~~text
选型编号：T1
来源：P1、D1
需要落实的能力与约束：引用作业一。
候选技术：至少两个具体方案。
比较维度：仅选择与来源问题相关的指标。
最终选择：明确到具体技术、组合或服务类型。
落地方式：说明接口、数据位置、格式、表结构或部署角色。
选择理由：说明官方资料、实验条件和权衡依据。
未满足项与补救措施：说明该技术无法解决的问题。
替换条件：说明出现哪些变化时需要重新选型。
~~~

可讨论的技术选型包括：

- 本地文件、HDFS 和对象存储。
- 文本、SequenceFile、Parquet 和 ORC。
- 普通文件、关系数据库、HBase 和 Hive 表。
- Hive 内部表和外部表。
- Hive、HBase、关系数据库和 Elasticsearch 的查询职责。
- 单 NameNode、HA NameNode 和云端托管存储。
- Hadoop/YARN、容器化运行和托管计算服务。

### 3.6 落地架构图

架构图必须展示入选技术如何协同工作，至少应包含：

- 用户、前端、Agent、任务接口和结果查询接口。
- Hadoop/MapReduce 作业的提交与运行方式；必要时标出 YARN 或其他资源管理组件。
- NameNode、DataNode 与客户端之间的元数据访问和数据传输关系；若采用其他存储，则画出替代关系。
- 原始区、隔离区、清洗区、质量指标区和发布区。
- HBase、Hive、关系数据库或 Elasticsearch 中实际入选的组件及其查询职责。
- 主要文件格式或表模型。
- 若选择 HBase，给出 RowKey 和 Column Family 摘要。
- 若选择 Hive，说明分区或分桶依据。
- 高可用或备份、权限、监控、日志和数据校验中的至少三项。
- 数据流和控制流。
- 关键组件对应的 P、D 和 T 编号。
- 图例，用于区分实验必须实现、设计建议和远期设想。

图中不得只堆叠产品 Logo。每个组件都应标明职责，每条箭头都应注明传输的数据、调用或状态。图中还需明确哪个存储保存权威数据，以及哪些系统只保存索引、缓存或派生结果。
