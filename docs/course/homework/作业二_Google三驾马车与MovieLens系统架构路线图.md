# 作业二：Google 三驾马车的问题发现与设计决策路线图

本作业以小组为单位完成，每组提交一份。

## 1. 作业定位与边界

本周课程介绍 Google 三驾马车：Google File System（GFS）、MapReduce 和 Bigtable。三者分别从分布式存储、并行计算和结构化数据管理的角度，展示大规模系统如何应对硬件故障、数据增长、并发访问和性能需求。

本学期第一次实验要求构建 MovieLens 数据治理 Agent。用户通过前端提交自然语言请求后，Agent 调用 Hadoop 完成数据质量检查、数据清洗和清洗前后的五维质量评分，并返回真实结果及相应解释。

本作业聚焦实验前期的 **问题发现与设计决策**。你需要分析系统当前及未来可能面临的问题，说明问题的触发条件和影响，并参考 Google 三驾马车形成技术中立的设计决策。

下一次“大数据存储和处理”小作业聚焦 **具体技术选型**，届时再比较并选择 HDFS、HBase、Hive、MySQL、Elasticsearch、对象存储、文件格式和部署方式。本次作业不得提前给出具体的产品组合。

| 本次作业负责 | 下一次作业负责 |
| --- | --- |
| 发现并定义系统问题 | 根据问题比较具体技术 |
| 分析问题的触发条件、影响和优先级 | 选择系统、组件、格式和服务 |
| 作出技术中立的设计决策 | 将设计决策落实为技术方案 |
| 提出存储、计算、查询和恢复所需的能力 | 设计目录、表、RowKey、列族、分区、分桶和索引 |
| 绘制逻辑架构并划分能力边界 | 绘制组件架构和部署拓扑 |
| 说明决策的验收条件和保留风险 | 说明配置、迁移、运维和回退方法 |

本作业不要求实现所设计的架构。实验仍以实验文档规定的基础功能为准，完成基础功能即可获得实验部分的满分。本作业中的未来设想不会成为实验的额外实现要求。

## 2. 总体要求

围绕以下问题完成一份架构设计文档：

> MovieLens 数据治理 Agent 当前及未来可能面临哪些存储、计算、数据组织、故障恢复和可信性问题？这些问题会在什么条件下发生，并造成什么影响？参考 Google 三驾马车后，系统需要作出哪些技术中立的设计决策？下一次技术选型需要提供哪些能力？

文档应形成清晰的推理链：

> 工作负载与场景 → 问题及证据 → 设计决策 → 所需能力 → 逻辑架构 → 分阶段演进

问题使用 P1、P2 等编号，设计决策使用 D1、D2 等编号。每项设计决策必须引用一个或多个问题编号。下一次作业将继续引用这些编号完成技术选型。

## 3. 详细要求

### 3.1 问题发现

至少发现 6 个对本系统有实际意义的问题。不得仅使用“性能不好”“可靠性不足”等抽象表述。

每个问题至少应说明：

| 项目 | 要求 |
| --- | --- |
| 问题编号 | 使用 P1、P2 等唯一编号 |
| 现象或风险 | 说明可能发生的情况 |
| 触发条件 | 说明发生问题时的数据规模、并发量、故障或使用方式 |
| 影响对象 | 说明受影响的是数据、任务、Agent、用户还是运维人员 |
| 影响结果 | 说明是否会导致错误、丢失、重复、延迟、不可追溯或成本增加 |
| 判断证据 | 说明依据来自实验需求、课堂机制、工作负载推演还是调研资料 |
| 优先级 | 说明为何现在处理、以后处理或暂不处理 |

问题至少覆盖以下四类：

- **存储问题：** 数据增长、元数据瓶颈、节点失效、数据丢失或版本混用。
- **计算问题：** 任务切分、数据传输、慢任务、失败重试或重复执行。
- **数据组织问题：** 查询模式、多版本结果、数据布局或历史结果管理。
- **系统可信性问题：** Agent 编造结果、任务状态不一致、证据不可追溯或正式结果被覆盖。

### 3.2 课堂知识与问题映射

GFS、MapReduce 和 Bigtable 三部分均须涉及，且每部分至少选择两个具体机制进行分析。

| 课堂主题 | 可分析的机制 | 可用于发现的问题 |
| --- | --- | --- |
| GFS | 单 Master、Chunk、副本、心跳、操作日志、追加写、一致性模型、客户端直接访问 ChunkServer | 元数据瓶颈、节点故障、数据恢复、并发写入和版本一致性 |
| MapReduce | 任务划分、Shuffle、数据本地性、失败重试、推测执行、任务粒度 | 并行效率、网络开销、慢任务、重复执行和中间结果管理 |
| Bigtable | 行键、列族、时间戳多版本、Tablet、SSTable、MemTable、提交日志、Compaction、Bloom Filter | 查询模式、数据热点、历史版本、写入恢复和读取效率 |

对每个选定的机制回答以下问题：

1. 该机制解决了什么问题？
2. 它依赖哪些工作负载或系统假设？
3. 它会带来哪些限制或新问题？
4. MovieLens 数据治理 Agent 是否存在类似问题？依据是什么？
5. 由此需要形成哪些设计决策或能力要求？

### 3.3 工业界演进调研

除课堂内容外，选择一条相关的当前业界的前沿技术路线进行调研。参考方向如下：

- 集中式元数据向高可用或分布式元数据演进。
- 多副本向纠删码或分层存储演进。
- MapReduce 向 DAG、批流统一或存算分离演进。
- “计算靠近数据”理念在云环境中的变化。
- Bigtable 思想在现代宽列存储和 LSM 系统中的延续。
- 面向 Agent 的异步任务、幂等性、可追溯证据、人工确认和失败恢复。

所选方向至少应说明：

- 经典方案原本解决什么问题。
- 工作负载发生了什么变化。
- 新方案解决了哪些旧问题，又引入了哪些新问题。
- 哪些结论适用于本系统，哪些结论仅适用于更大规模或不同场景。

### 3.4 设计决策记录

至少写出 4 项技术中立的设计决策。每项决策必须引用前文的问题编号。

~~~text
决策编号：D1
关联问题：P1、P3
设计决策：说明系统在逻辑上决定做什么。
所需能力：说明下一次技术选型必须提供哪些能力。
约束：说明规模、延迟、成本、一致性或课程实验限制。
依据：说明课堂机制、调研证据和工作负载推演。
代价与保留风险：说明该决策仍无法解决的问题。
验收条件：说明哪些现象或指标能够证明决策有效。
触发重评的条件：说明出现哪些变化时应重新评估决策。
~~~

可讨论的设计决策包括：

- 是否需要将元数据管理与数据读写分离。
- 在什么情况下必须保留冗余数据或恢复信息。
- 任务失败后允许从头执行，还是必须支持部分恢复。
- 计算是否必须靠近数据，以及何时允许存算分离。
- 正式结果是否必须保持不可变并保留历史版本。
- Agent 是否必须采用异步任务状态模型。
- 系统是否必须识别重复请求并保证幂等发布。

### 3.5 逻辑架构图

架构图用于汇总问题和设计决策，至少应包含：

- 用户、前端、Agent、数据处理能力和结果服务等逻辑角色。
- 原始数据、清洗数据、质量结果和报告之间的数据流。
- Agent 提交任务、查询状态和获取结果的控制流。
- 元数据与实际数据的职责边界。
- 关键位置对应的 P、D 编号。
- 图例，用于区分当前实验能力、设计要求和未来设想。
